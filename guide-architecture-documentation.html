Architecture documentation that people actually read

Create documentation that helps people decide, build and operate.

You'll come away with:

  • How to define the reader and purpose before choosing a format
  • A clear structure for explaining context, decisions and consequences
  • How to use C4 and other diagrams at the right level
  • Ways to keep documentation useful without duplicating every detail

Documentation should help someone act

Architecture documentation is useful when it helps someone understand the service, make a decision, build the intended design, assess a risk or operate the result. Producing a document is not the outcome. The outcome is shared understanding and a traceable basis for action.

The Service Standard expects teams to show that they have made good technology decisions. The Technology Code of Practice provides criteria for designing, building and buying government technology. Documentation can provide evidence for both, but no single template proves that a design is sound.

Documentation loses value when it:

  • has no clear reader, question or decision
  • describes generic layers without naming real systems and responsibilities
  • mixes overview, design detail and operational instruction on one page
  • presents the chosen approach without its constraints or trade-offs
  • duplicates information that changes elsewhere and becomes stale

Length is not the problem by itself. A short document can omit the evidence a reader needs, while a detailed design may need substantial depth. The test is whether each section has a purpose and whether the reader can find the important information quickly.

A document earns its place when a named reader can use it for a named purpose.

Write for a reader and a purpose

Start by asking who needs the information, what they need to do with it and when they will use it. Those answers determine the format, language and level of detail.

Senior decision-makers may need the outcome, cost, dependencies, major risks and decisions requiring authority. Delivery teams need boundaries, responsibilities, interfaces, constraints and enough detail to build without guessing. Security and privacy specialists need data flows, trust boundaries, classifications, threats and controls. Operations teams need deployment, monitoring, support and recovery information. Future teams need the reasoning, current status and known limitations.

This does not mean writing a separate document for every group. Use a concise overview for the shared picture, then link to details such as decision records, interface specifications, threat models and runbooks. State the intended audience at the start and make the route to supporting material obvious.

Create the smallest useful set

Minimum viable documentation is not a fixed page count. It is the smallest set of reliable information that supports the work and meets applicable governance, assurance and operational needs.

A useful architecture overview will often cover:

  • the purpose, scope and system boundary
  • important user needs, requirements and quality expectations
  • constraints, assumptions and unresolved questions
  • the main components, data, integrations and deployment environment
  • significant decisions, options considered and accepted trade-offs
  • security, privacy, resilience and operational implications
  • risks, owners, dependencies and next decisions
  • document owner, status and last verified date

Not every item must sit in one file. Link to an authoritative source instead of copying it. For example, keep interface detail in the API specification, operating procedures in the runbook and significant decisions in Architecture Decision Records. The government's Architectural Decision Record framework uses context, decision and consequences to make important choices visible and traceable.

If your organisation mandates a template, use it without padding empty sections. Mark an item as not applicable and explain why, or link to the source that owns the detail. Concision should remove duplication and filler, not evidence.

If a section has no reader, purpose or decision behind it, question why it exists.

Organise around context, decisions and consequences

A simple structure works at several levels of detail:

  • Context: What problem are we solving? What is in scope? Which requirements, constraints and assumptions shape the choice?
  • Decision: What has been chosen, by whom and on what evidence? Which credible alternatives were considered?
  • Consequences: What becomes easier or harder? Which costs, risks, dependencies and future actions follow?

A description tells the reader what the architecture contains. A decision explains why it has that shape. Both matter, but they answer different questions. Keep the overview readable by summarising significant decisions and linking to the full records.

The GDS guidance on documenting architecture decisions recommends keeping decisions in version control and preserving their context and consequences. When a later decision replaces one that has already been implemented, retain the history rather than rewriting the old record as though the first decision never happened.

Draw diagrams with one clear purpose

A diagram should answer a specific question. Decide whether it shows scope, structure, data movement, runtime behaviour, deployment, security boundaries or something else. Combining all of these usually makes the result harder to read.

The NCSC's guidance on drawing good architecture diagrams recommends simple views, clear language, logical grouping and a shared authoritative source. Apply those ideas by:

  • using a title that states the purpose and viewpoint
  • showing the boundary and identifying what is outside the scope
  • naming real components and their responsibilities
  • labelling relationships with what moves or happens
  • using a small, consistent notation and explaining unfamiliar symbols
  • separating current, interim and target states

Do not rely on colour alone to convey meaning. The GOV.UK Design System guidance on images explains that complex diagrams need short alternative text and a longer description that makes the same information available in text.

Use the C4 model where it helps

The C4 model, created by Simon Brown, provides four levels of zoom for software architecture:

  • System context: the system, its users and the other systems around it.
  • Container: the major applications and data stores inside the system, their responsibilities and communication.
  • Component: the main components inside one container and how they work together.
  • Code: implementation detail for a component, where a code-level diagram adds value.

You do not need all four levels. The C4 guidance says system context and container diagrams are sufficient for most software development teams. Add component or code diagrams only when they explain something that is otherwise difficult to understand.

C4 describes static software structure. It also offers supporting dynamic and deployment diagrams, but it does not replace every view. A service may still need data flows, user journeys, network views or operational sequences. Choose the view from the question, not from the diagramming method.

Keep documentation aligned with the service

Documentation becomes unreliable when the service changes and the explanation does not. A stale diagram can be more damaging than a missing one because readers may treat it as current.

Give important documentation an owner, status and last verified date. Define the events that require review, such as a changed decision, new integration, material security finding, deployment change or revised operating model. Tie the update to the delivery workflow rather than relying only on a calendar reminder.

Keep each kind of detail with the source best able to maintain it. Version-controlled documentation can sit near the code it explains. Runtime configuration should remain in controlled configuration, API contracts in an interface specification and operational procedures in a runbook. The architecture overview should connect these sources and explain their significance.

Diagrams as code can make changes easier to review, version and reproduce. It does not guarantee that a diagram matches the running service; the team must still update and verify its source. Whatever the tool, keep one discoverable authoritative version and archive or label superseded views clearly.

Questions to ask before publishing

  • Who is the primary reader and what will they use this for?
  • Can they find the scope, status and important decisions quickly?
  • Does the document name the real systems, interfaces and owners?
  • Are requirements, assumptions, decisions and open questions clearly separated?
  • Do the diagrams each have one purpose, clear labels and an accessible explanation?
  • Are current, interim and target states easy to distinguish?
  • Have duplicated details been replaced with links to authoritative sources?
  • Are significant trade-offs, risks and consequences visible?
  • Who will maintain the document and what changes will trigger a review?
  • Can anything be removed without losing evidence or making a decision harder?

This guide describes practical architecture documentation for Solution Architects working around UK government services. The suggested structure and questions are teaching aids rather than a mandatory document template.
