I went to AWS Summit Washington, D.C. expecting agentic AI to dominate the agenda, and it did, with agents turning up in one form or another in session after session. The session that stayed with me, though, was one of the least flashy. It was about spec-driven development with a tool called Kiro, and about whether AI-assisted development can be given enough structure to build real systems, the kind that someone has to secure, maintain and operate for years after the demo. That question is where things get interesting for architects, and if you'd like the runtime side of the same story, I've written separately about [Amazon Bedrock AgentCore and the production gap for AI agents](/amazon-bedrock-agentcore-and-the-production-gap-for-ai-agents).

# **The trouble with vibe coding**

Vibe coding is an unkind name (although I have heard it being called worse) but a fairly accurate one, because it describes a loop most of us have tried by now. You describe what you want, the AI produces some code, you run it, and you keep prompting until the result looks right. For a prototype or an experiment that's perfectly fine, the trouble only really starts when the prototype quietly becomes the product, because nothing in that loop ever forced anyone to make a decision on the record.

Look closely at what that loop leaves behind and the problem becomes clear, because a prompt is closer to a wish than a requirement, a chat history won't pass for a design document, and a passing test only proves that the code does what the code does, which may bear little resemblance to what the business originally asked for. With these tools the code usually looks convincing long before the design is sound, and Kiro's answer is to move the weight of the work away from the conversation and onto a specification.

# **Putting a specification first**
 
It's worth saying up front that Kiro doesn't force this on you. A new session [starts as an ordinary conversation](https://kiro.dev/docs/ide/setup/), so you can vibe code in Kiro as happily as anywhere else, and the structured workflow is something you choose. When you do choose a [spec](https://kiro.dev/docs/specs/), Kiro works through three documents before it builds anything. The first, requirements.md, captures what needs to be built as user stories with acceptance criteria, written in a structured style called EARS that reads along the lines of "when this happens, the system shall do that". Once you're happy with those, design.md sets out how the solution should work, covering the architecture and components, data models and interfaces, error handling and testing strategy, and tasks.md then breaks that design into discrete, trackable pieces of implementation work. You review and confirm each document before moving on to the next.
 
On paper that's a small change, but in practice it's the difference between letting the AI leap from a vague idea straight to working code and making it walk through requirements, design and implementation in order, which is how a properly run delivery works anyway. The workflow has also become more flexible since it launched. If you already have a technical design you can [start from the design instead](https://kiro.dev/docs/specs/best-practices/), there's a separate spec type for bug fixes, and a Quick Spec option generates all three documents in one pass without stopping for approval.
 
The clearest message from the session was also the least fashionable one, which was simply to plan before you build. That shouldn't need saying, but AI tools make it remarkably easy to skip, because when a tool can generate a working screen or API in minutes, planning starts to feel like delay. The visible result arrives so quickly that the difficult work seems already done, when in truth the difficult part is deciding what happens off the happy path. What happens when the data is incomplete, who is allowed to perform the action, what gets logged, what happens when the service next door is unavailable, and who supports all of this once the original developer has moved on? No amount of generated code answers those questions, and a specification gives you a pause in which to ask them before the assumptions harden into code.
 
Take a request as innocent-sounding as "create a secure login page". It seems clear until you ask what secure means here, whether you need multi-factor authentication, which identity provider you're using, how long a session should last, what happens after five failed attempts, what gets written to the logs and what the accessibility requirements are. Leave all of that open and the AI fills the gaps itself, sometimes sensibly and sometimes with choices that are flatly unsuitable for your organisation, and you only find out later. Structured requirements drag those assumptions into the light before implementation begins, and Kiro now has an optional [requirements analysis](https://kiro.dev/docs/specs/) step that checks requirements.md for inconsistencies, ambiguities and gaps before the design is drawn up.
 
# **A design you can argue with**
 
Once the requirements are agreed, Kiro produces the design and breaks it into tasks, and for me this is the part that makes it more relevant to architects than most AI coding tools, because the design becomes something you can argue with. You can check it against the existing estate and ask whether the security controls are adequate, whether the proposed technology is on the approved list, and whether the interfaces and data flows make sense. None of that means accepting the generated design as given, but it does mean there's something concrete to review before the code exists.
 
What the process leaves behind is just as valuable. You end up with a written trail from requirement to design to task, and if the requirements change, Kiro can [sync the task list](https://kiro.dev/docs/specs/best-practices/) so that new tasks map to the new requirements. In the IDE it can also pick out the requirements that can be logically tested and turn them into optional [property-based tests](https://kiro.dev/docs/specs/correctness/), which throw hundreds or thousands of random inputs at each rule rather than the handful of examples a person, or an AI, happens to think of. That trail earns its keep during assurance, testing, handover and every future change, because the team has a record of why something exists instead of having to reverse-engineer the answer from the code.
 
# **Standards, access and automatic checks**
 
Three more features round out the picture, and each one maps neatly onto a familiar governance concern, starting with steering. [Steering files](https://kiro.dev/docs/steering/) are Markdown documents, kept in the project or in your home folder, that give the AI persistent knowledge such as the approved technology stack, the repository structure, coding standards, testing approach, security requirements and architectural principles. You decide whether each file is always included, included only when matching files are being worked on, or loaded only when needed, which deals with a common weakness in these tools, namely that they behave as though every conversation is the first one. It doesn't guarantee compliance, but it beats leaving the standards in a document nobody opens, and it hints at something architects have wanted for years, which is principles that the tooling actually applies rather than principles that live on a wiki.
 
The second is the Model Context Protocol (MCP), which lets Kiro connect to external tools and information sources such as current documentation, repositories, APIs and internal standards. That gives the AI much better context, but it also raises fresh governance questions about which systems it can reach and with what permissions, which sources count as authoritative, what it can retrieve or change, and how all of that is audited. Kiro gives you some of the levers, since each [MCP server configuration](https://kiro.dev/docs/mcp/configuration/) can list which tools run without asking and which are disabled altogether, and in the IDE and CLI, permission rules follow a [deny-wins approach](https://kiro.dev/docs/configuration/) across every scope. The more capable the assistant becomes, though, the more identity, access control and audit matter, and connecting an AI tool to real systems without clear boundaries is asking for trouble.
 
Finally there are [hooks](https://kiro.dev/docs/hooks/), which run a shell command or an agent prompt automatically when something happens in a session, such as the agent invoking a tool or, in the IDE and CLI, saving a file or finishing a spec task, so you can wire in tests, formatting, security scans or checks against project standards. None of those controls is new in itself, but here they sit inside the AI-assisted workflow instead of being left until the end, when problems are more expensive to fix. It's worth knowing, though, that file-based hooks fire on the agent's changes and [not on edits a developer makes by hand](https://kiro.dev/docs/hooks/types/), so they complement your pipeline checks rather than replacing them.
 
# **What this means for architects**
 
There's a tendency to talk about AI development tools as though they remove the need for architecture, and I'd bet on the opposite. As implementation gets faster, poor decisions get implemented faster too, so a weak requirement becomes working code in minutes and a bad pattern can spread across an entire codebase before anyone has had the chance to challenge it.
 
Standing in front of the technology to slow it down is a losing game, and the wrong one anyway. The job is to make sure the acceleration happens in the right direction, by defining the constraints the AI works within, reviewing the designs it generates, deciding which tools and data it can touch and keeping human accountability unambiguous. An AI tool can suggest an architecture, but it can't accept the organisational risk when that architecture fails.
 
That's also why code generation is the least interesting thing about Kiro, since plenty of tools generate code. What deserves attention is the structure around the generation, from requirements, design and tasks through to persistent standards, controlled sources, automated checks and tests that verify the intended rules rather than a few examples. Vibe coding is fine when the result is disposable, but for anything that has to be secure, maintained, assured or operated by a team it won't do. The future of AI-assisted development is unlikely to be a blank prompt box we keep typing into until an application looks finished, and far more likely to be a controlled engineering process in which requirements, designs, standards and tests shape what the AI is allowed to produce. That's delivery discipline as it has always been, with the difference that it's finally becoming executable.
